# Backtesting dashboard

Compares credit-risk model projections against realised outcomes, by vintage and
projection horizon.

## Purpose
For each metric (PD, PD CRR, LGD, EAD, NCO), collapse facility-grain forecasts to
a portfolio value per quarter, find the realised outcome for each target quarter,
and report the error — signed, absolute and percentage — plus bias / MAE / RMSE /
MAPE / hit-rate summaries at any grouping level.

## Charts

Sixteen figures, all built to the monitoring dashboard's recipe — the
`_make_dual_panel_figure` layout, `build_pd_time_series_xaxis` quarter axis,
`_monitoring_trend_line_color`, RAG-coloured markers via `pd_rag_color`, and
`_apply_transparent_background` so the card's themed surface shows through.

| Where | Chart | Reads |
|---|---|---|
| Overview | **Cumulative loss performance** | Static-pool view: NCO accumulated through each horizon as a share of that vintage's opening exposure, every cohort aligned at age 0 |
| Each metric section | **Forecast vs actual** | Realised outcome (solid) against every vintage's forecast of it (dashed), with each forecast's percentage error beside it |
| Each metric section | **Error by projection horizon** | MAPE on the left, mean signed bias on the right |
| Each metric section | **By vintage** | That metric's projected path per cohort, against age |

Two deliberate choices:

- The horizon chart plots **MAPE, not MAE**. Exposure-weighted aggregation
  diversifies away the facility-level noise that grows with horizon, so
  aggregate MAE is not monotone even when the underlying error is. MAPE is
  scale-free and keeps the horizon effect visible.
- Vintage curves carry **end-of-line labels** as well as a legend, de-collided
  against the axis range so converging cohorts stay readable. Only the label
  moves; the curve and every hover value stay where the data puts them.

Figure *shapes* live in `shared/ui/charts.py` beside the monitoring and SAAS
builders (that module owns the theme palette and the dual-panel layout);
`ui/views/figures.py` is a thin wrapper that only picks each metric's value
format — rates as percentages, EAD/NCO as currency.

## Data source

`source_data/backtesting_results.xlsx` — five facility-grain result sheets.
Documented in full in `source_data/Backtesting_Workbook_Guide.md`; generated by
`source_data/generate_backtesting_data.py` and checked by
`source_data/verify_backtesting.py`.

Sheet and column names live in `shared/domain/constants.py`; the file location is
`settings.backtesting_results_file`. Loading happens in
`repositories/loader.py`, exposed once via `data_access.BACKTESTING_PAGE_DATA`.

### The workbook is aligned to the model catalogue

`model_names` says which segments each PD model serves, and
`generate_backtesting_data.py` builds the facility population to match, so a
catalogue-driven cascade can never offer a combination with no rows.

**O&M is absent from this dashboard**: no PD model in the catalogue covers it,
and a facility with no PD cannot be backtested. The workbook therefore carries
Cyclical and Defensive only.

**Only the PD side is aligned.** The catalogue confines LGD models to O&M and
EAD models to Defensive, so aligning those too would leave *no* segment with a
full PD+LGD+EAD triple — exposure weighting would have nothing to weight with
and the NCO identity would be uncomputable everywhere. LGD and EAD therefore
cover the same facilities the PD sheets do.

### Three properties of the data that shape this feature

1. **`Quarter == 0` is the realised anchor.** It holds the observed value at the
   snapshot date and is identical across scenarios and J/N flags. The actual for
   target quarter *T* is the anchor row of the vintage whose quarter *is* *T*.
2. **`results.pd` and `results.pd_crr` cover disjoint facility populations**
   (one PD model each). A portfolio-level PD is the union of both — neither
   sheet alone covers the book, so the Model filter offers models from both.
3. **Exposure lives only on `results.ead`.** PD and LGD are exposure-weighted, so
   the weight is joined from that sheet on the run identity *excluding*
   `Model Name` (a facility's PD model is not its EAD model).

## Filters

**Primary row:** Region, Portfolio, Model Group, Model, Segment.
**Secondary row:** Model Use Case / Cycle, Scenario, J/N Flag, Month End Snapshot.

Options are derived from data, never hard-coded. The scope filters come from the
**model catalogue** (`model_names` in `dummy_mev_data.xlsx`) — the same sheet
Monitoring and SAAS read — so all three dashboards share one model vocabulary.
Cycle / Scenario / J/N Flag / Month End Snapshot come from
`backtesting_results.xlsx`.

Models are shown by their **Model Descriptive Name** ("PD Model A"); the option
*value* stays the raw key (`PD_model_a`) so it still matches the workbook
without a reverse lookup.

A model whose catalogue attribute is blank shows as **Unassigned** and sorts
last, rather than being dropped — `PD_model_b` has no Portfolio, so selecting a
real portfolio excludes it, which is the honest reading of a missing value.

**"Model Use Case / Cycle" is a UI-only label**, matching the same rename in
Monitoring. The Dash element id (`bt-run-for`), the applied-filter key
(`run_for`) and the workbook column (`Run For`) are unchanged.

Nothing renders from the live filter values: **Apply filters** snapshots them
into `bt-applied-filters-store`, and the section stack is a pure function of that
snapshot. Same interaction model as SAAS and the PD page.

### Analysis grain contract

`All` has an explicit meaning for every filter dimension. A dimension marked
**combine** describes disjoint pieces of one population and is collapsed before
an aggregate is calculated. A dimension marked **compare** describes alternative
observations and remains in the aggregate key; it must never increase an EAD or
NCO total as though it introduced more facilities. A **primary selection** is a
single governed path rather than a population dimension.

| Filter dimension | Meaning of `All` | Aggregate behavior |
|---|---|---|
| Region | **Combine** | Union the disjoint model populations in every region surviving the catalogue scope. |
| Portfolio | **Combine** | Union the disjoint model populations in every portfolio surviving the catalogue scope. `Unassigned` remains an explicit population. |
| Model Group | **Combine** | Union the disjoint model populations in every selected model group. |
| Model | **Combine** | Union disjoint PD-model facility populations. For LGD/EAD/NCO the same union is applied by facility scope; model partitions are collapsed, not added as repeated runs. |
| Segment | **Combine** | Union segment populations. Rate metrics are exposure-weighted across the union; EAD and NCO are summed once across its facilities. |
| Model Use Case / Cycle (`Run For`) | **Compare** | Keep one aggregate series and one set of error records per cycle. Never sum cycles together. |
| Scenario | **Primary selection** | Base is the only accuracy path. `All` resolves to Base for scoring and raw default context; an explicitly selected non-Base scenario remains context-only and has no accuracy statistics or RAG. |
| J/N Flag | **Compare** | Keep J and N as separate aggregate series and error records. Never sum or exposure-weight them together as extra facilities. |
| Month End Snapshot | **Compare** | Keep each forecast vintage separate. `All` compares vintages; a selected snapshot narrows forecasts while actual anchors still resolve from full comparable history. |

The resulting aggregate grain is therefore
`(Month End Snapshot, Run For, Scenario, J/N Flag, Quarter)` after the combine
dimensions have been collapsed. Scenario is Base on every scored record. This
contract applies equally to the score inputs, raw vintage context, and the two
static-pool series; those surfaces may present the comparison dimensions
differently, but none may aggregate across them.

**Scenario defaults to `Base`.** A backtest scores the base scenario; the others
are deliberately conservative, so comparing them to realised outcomes measures
the conservatism buffer rather than model accuracy. They stay selectable for
context.

### The scope cascade

`Region → Portfolio → Model Group → Model ⇄ Segment`. Model narrows Segment *and*
Segment narrows Model, so this is the two-way case in `CLAUDE.md` callback
rule 2: reading either filter's `value` as an `Input` would close the loop and
produce a dependency cycle. Everything triggers on the option buttons'
`n_clicks` instead.

**One callback, not five.** Every single-select option button shares the same
pattern `type`, so a single pattern `Input` matching *all* of this page's filters
catches the click and dispatches on `ctx.triggered_id["filter"]`. Five separate
callbacks would each need to write Model's and Segment's options, leaving four
callbacks fighting over one output.

The traps, and how each is handled:

- The picked value is read from `ctx.triggered_id`, **not** from `State` —
  `select_single_select_option` writes the value in the same round trip, so
  `State` still holds the *previous* one.
- The remount fires the pattern `Input` with every `n_clicks` still `0`; the
  guard short-circuits before touching `ctx` at all.
- Rule 3 is satisfied trivially: the only `Input` is that one pattern, so
  nothing from outside a callback-rendered container is mixed in.
- The callback never rewrites the filter that was just clicked — that value
  belongs to `select_single_select_option` for this round trip.

**The catalogue drives the cascade**, not the results workbook, and the workbook
is generated to agree with it (see below). So picking Segment = Defensive offers
only PD Model B, and picking PD Model A offers only Cyclical.

## Styling

- `assets/backtesting.css` — only the genuinely new components, all `bt-`
  prefixed. Colours come from the existing `:root` variables in `styles.css`; no
  new variables and no new palette.
- Two constraints that file documents: Dash serves assets alphabetically so
  `backtesting.css` loads *before* `styles.css` (a `bt-` rule cannot outrank a
  generic one at equal specificity), and only the `:root` variables re-bound
  under `.monitoring-shell.theme-dark` flip with the theme — `--pd-blue` and
  `--pd-blue-soft` do not, and are unused here.
- `assets/js/backtesting_subnav.js` — sub-nav scroll-spy for `#bt-subnav`,
  modelled on `monitoring_pd_subnav.js`.

## Conventions

- `register_callbacks(app)` is idempotent via `shared.registration`.
- The page keeps its `dcc.Store`s inline in its own layout, so
  `stores.build_stores()` returns `[]`.
- All element ids carry a `bt-` prefix, so nothing collides with monitoring's
  `pd-*` or SAAS's `saas-*` ids.

## How to add a section

1. Add the anchor id and its `(index, title, description)` to `METRIC_SECTIONS`
   (or a new group) in `ui/views/backtesting.py`.
2. Add the anchor to `SUBNAV_GROUPS` in the same module **and** to `SECTION_IDS`
   in `assets/js/backtesting_subnav.js` — the script tracks an explicit list.
3. Page-only logic → `domain/`; heavy output generation → `services/`.
4. Add a layout-builds assertion under `tests/`.
